# 의사결정 기록 — 고객센터 메일 답장 워크플로우

각 결정은 문제/맥락 · 선택지 · 판단 기준 · 결정 · 근거 · 결과/대가 · 재검토 조건의 일곱 칸으로 적습니다.

---

## 결정 1 — 답장 초안을 누가 검사하는가

| 칸 | 내용 |
|---|---|
| 1. 문제 / 맥락 | 요구사항 R4는 주문번호와 처리 기한이 빠진 답장이 고객에게 나가는 것을 막습니다. 검사하는 자리에 무엇을 앉힐지 정해야 합니다. 고객센터는 하루에 들어오는 메일을 당일에 처리해야 하고, 팀장은 답장을 모두 읽을 시간이 없습니다 |
| 2. 선택지 | ① 검사 노드를 두지 않고 draft 노드의 시스템 지침만 강화한다 ② evaluate 노드에 사람 승인을 앉힌다(`interrupt()`로 담당자에게 판정을 받는다) ③ evaluate 노드에 LLM 평가자를 앉힌다(평가자-최적화자 패턴) |
| 3. 판단 기준 | ㉠ 담당자의 작업 시간이 메일 수에 비례해 늘어나지 않을 것 ㉡ 주문번호 누락을 실행 중에 잡아낼 것 ㉢ 판정 결과가 실행 기록에 남아 원인을 추적할 수 있을 것 |
| 4. 결정 | 선택지 ③을 채택합니다. evaluate 노드에 LLM 평가자를 앉히고, 반려 사유를 상태에 실어 draft 노드로 되돌립니다 |
| 5. 근거 | 선택지 ①은 기준 ㉡을 만족하지 못합니다. 지침을 강화해도 누락이 발생했는지를 실행 중에 확인하는 단계가 없습니다. 선택지 ②는 기준 ㉠을 만족하지 못합니다. 담당자가 모든 답장을 판정해야 하므로 작업 시간이 메일 수에 비례합니다. 선택지 ③은 기준 세 가지를 모두 만족하며, 판정 값과 반려 사유가 상태에 남아 기준 ㉢을 만족합니다 |
| 6. 결과 / 대가 | 얻는 것: 주문번호와 처리 기한 누락을 발송 전에 잡아내고, 반려 사유가 실행 기록에 남습니다. 치르는 것: 메일 한 통당 LLM 호출이 최소 1회 늘어나며, 반려가 발생하면 호출이 더 늘어납니다. 평가자가 잘못 판정할 가능성을 감수합니다 |
| 7. 재검토 조건 | ㉮ 평가자의 오판정 비율이 실행 기록 100건 기준 5건을 넘으면 재검토합니다 ㉯ 답장에 금액을 확정해 적는 기능이 추가되면, 사람 승인(선택지 ②)을 함께 두는 구성으로 재검토합니다 |

## 결정 2 — 되돌림 루프를 언제 끝내는가

| 칸 | 내용 |
|---|---|
| 1. 문제 / 맥락 | 결정 1로 evaluate 노드가 draft 노드로 되돌리는 루프가 생겼습니다. 되돌림을 끝내는 조건을 정하지 않으면 워크플로우가 종료되지 않습니다. 요구사항 R6은 되풀이가 끝나지 않는 상태를 막습니다 |
| 2. 선택지 | ① 합격 판정이 나올 때까지 되돌린다(횟수 제한 없음) ② 초안 작성 횟수 상한(`attempt == 3`)에 도달하면 끝낸다 ③ 실행 시작부터 60초가 지나면 끝낸다 |
| 3. 판단 기준 | ㉠ 종료 조건을 코드가 참·거짓으로 판정할 수 있을 것 ㉡ LLM 호출 비용의 상한을 메일 한 통 단위로 예측할 수 있을 것 ㉢ 종료했을 때 담당자가 후속 조치를 알 수 있을 것 |
| 4. 결정 | 선택지 ②를 채택합니다. 상한은 3으로 두고, 상한에 도달하면 발송하지 않고 `status`에 `"담당자 확인 필요"`를 쓴 뒤 종료합니다 |
| 5. 근거 | 선택지 ①은 기준 ㉡을 만족하지 못합니다. 평가자가 계속 반려하면 호출이 무한히 늘어납니다. 선택지 ③은 기준 ㉠을 만족하지만 기준 ㉡을 만족하지 못합니다. 같은 60초 안에 호출이 몇 번 일어나는지가 응답 속도에 따라 달라집니다. 선택지 ②는 호출 횟수의 상한이 초안 작성 3회로 고정되어 기준 세 가지를 모두 만족합니다 |
| 6. 결과 / 대가 | 얻는 것: 메일 한 통당 LLM 호출 횟수의 상한이 고정되고, 상한 도달 건이 담당자 확인 대상으로 남습니다. 치르는 것: 세 번째 초안도 반려된 메일은 자동으로 처리되지 않고 담당자에게 넘어갑니다 |
| 7. 재검토 조건 | ㉮ 상한 도달 건이 전체 메일의 10%를 넘으면 상한 값과 draft 노드의 시스템 지침을 함께 재검토합니다 ㉯ 답장 종류가 환불·배송 외로 늘어나면 종류별로 상한을 다르게 둘지 재검토합니다 |
